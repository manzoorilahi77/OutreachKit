Running it: one server, one database

No per-laptop installs and no GitHub sync. The app runs once, on a Hostinger VPS, behind Nginx or Caddy with HTTPS, under pm2 or systemd. You and every teammate open the same URL in a browser and sign in — only the owner has the code.

What changed from the files-and-Sync design

No more "every laptop has every file"

The old design accepted that logins identify people but don't lock data, because every laptop pulled every folder. A single shared database removes that: a BD's browser is only ever shown their own leads by the server.

Changes are immediate, not "next sync"

A reset, suspension, role change or hand-off takes effect on a person's next click, not at a 30-minute sync or a button press.

Removing someone is one action

Disable the account. There's no separate "remove GitHub repo access" step, and nothing was ever copied onto a laptop to begin with.

Store stays the seam

src/lib/store/ is still the only code that touches stored data — pages and actions call createStore(actor), never SQL or fs directly. That seam is why swapping files for MySQL didn't touch the screens below.

Accounts and sessions

There's no sign-up page and no email. You (or an admin) create every account in Users and share the login in chat; it works for them at their very next sign-in.

Username and password

Usernames are 3–30 characters: lower-case letters, digits, dot and underscore, unique in the database.

Temporary password, shown once

The app makes it, saves only a scrambled hash of it, and shows it once with a Copy button. At first sign-in the person sets their own (10+ characters).

Signed in for 14 days

Counted from sign-in, then they sign in again. Signing out ends it at once. The session is a signed, HttpOnly cookie, re-checked against the user row on every request.

Admin actions end sessions at once

Reset, suspend, disable, enable and role change are re-checked on the account's very next request — there's no laptop to wait on and nothing to sync.

Where the data lives

One MySQL database, on the Hostinger VPS. src/lib/store/ is the only code that touches it: pages and actions call the Store (createStore(actor)), never SQL directly. fileStore.ts — the team/ files this page originally specified — is kept only as the reference implementation and as the one-time source for pnpm db:import-team; both pass the same contract suite (tests/contract/storeContract.ts), so the two never drift apart in behaviour even though only one of them runs in production.

Timestamps are UTC DATETIME(3), dates DATE; the app speaks ISO strings. A migration that has run anywhere is never edited — a change is a new numbered file in db/migrations/, and pnpm db:migrate refuses an edited one.

Decisions

The roles, territory and visibility decisions from 11 Oct all stand. One decision was reversed two days later, and one was added since.

✓

You are the owner and only Super Admin; one workspace

You create every account and share the login. Admins can help manage accounts below admin.

✓

Username and password, 14-day sign-in

Temporary password shown once and changed at first sign-in. Reset, suspend, disable and enable by you or an admin.

The original decision was "runs on each laptop, no database, synced through a private GitHub repo." A Hostinger VPS made that unnecessary: one server, one database, teammates just sign in. fileStore.ts stays as the reference implementation and the one-time import source.

✓

The app hides others' leads

The server returns each person only what their role allows — a stronger guarantee than the old "every laptop has every file, the app hides the rest."

D4
