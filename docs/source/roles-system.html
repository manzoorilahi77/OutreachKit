Running it on laptops: files and GitHub, no database

Nobody installs a database. Each person's work is saved as plain files in their own folder inside the project, and the app's Sync button moves those files through your private GitHub repo. A teammate needs only Node, Git and a GitHub account, and their Claude sets those up.

When it syncs

When the app starts, every 30 minutes while someone is signed in, and when they press Sync. It pulls, saves their folder to git, and pushes. If GitHub sign-in is missing or two changes clash, it stops without losing anything and shows the sentence to say to Claude, such as "Fix the Outreach Kit sync". Sync never pushes code, so a teammate can't change the app by accident.

What this setup can't do

Logins identify people; they don't lock data

Every laptop that pulls gets every folder. The app shows a BD only their own leads, but the files can be opened in any text editor. You accepted this.

Changes arrive at the next sync

A reset, suspension or new account reaches a teammate's laptop when it next syncs: at start, within 30 minutes, or on the button.

Removing someone fully means GitHub

Remove their access to the repo, then disable the account. They keep whatever was already on their laptop.

Lead contacts stay in git history

Business phone numbers and emails live in the repo's history for good. Keep the repo private.

When you get a server later, a database takes the place of the file storage. All file reads and writes go through one Store module, so the screens don't change.

Accounts and sessions

There's no sign-up page and no email. You (or an admin) create every account, sync, and share the login in chat.

Username and password

Usernames are 3–30 characters: lower-case letters, digits, dot and underscore. The username is also the name of that person's folder.

Temporary password, shown once

The app makes it, saves only a scrambled hash of it, and shows it once with a Copy button. At first sign-in the person sets their own (10+ characters).

Signed in for 14 days

Counted from sign-in, then they sign in again. Signing out ends it at once.

Admin actions end sessions

Reset, suspend, disable, enable and role change raise the account's revision number. A laptop holding an older number signs that person out at its next sync.

## Why this phase exists

Today the Outreach Kit is one person's tool: magic-link sign-in to any
email, every row private to its owner, data in Supabase, the lead finder in
MySQL. Famysys now runs it as a team, with constraints the owner has set:

- **There is no server.** Every teammate runs the app on their own laptop,
  Mac or Windows.
- **Teammates are not technical.** They clone the repo and ask their own
  Claude to run it. They must never install, see or manage a database.
- **The owner creates every account** (username and temporary password),
  pushes, and shares the login in chat. A teammate pulls and signs in.
- **Team data moves through GitHub.** Each person's work is pushed to the
  repo so the owner and managers can see it.

So this phase removes Supabase and MySQL from the app and stores everything
as files in the repo, one folder per person, synced by the app with git.

## How it works (read before anything else)

```
team/
  schema.json                 { "version": 1 }   file-format version
  workspace.json              studio, demo domain, based line   (admins write)
  teams.json                  teams and their managers          (admins write)
  users/<username>.json       role, team, status, temp password hash, rev   (admins write)
  data/<username>/            written ONLY by that person's app
    profile.json              default device; own password hash + basedOnRev
    kits/<id>.json            saved kit: inputs + title, status
    leads/<id>.json           one lead: the 28 columns, checks, stage, sequence
    events.jsonl              stage changes, touches, comments (append-only)
    assignments.jsonl         hand-offs this person made (managers, admins)
    audit.jsonl               account and export actions this person took
    playbook.json             read receipts
    finder/businesses.jsonl   lead finder results (replaces MySQL)
    finder/runs.jsonl
.local/                       gitignored: session secret, last-sync state
```

- **Each person writes only their own folder.** Admins and super admins
  also write `team/users/`, `team/teams.json` and `team/workspace.json`.
  Because nobody writes another person's files, syncs don't conflict.
- **State that involves two people is derived, never cross-written.** A
  manager assigning a researcher's lead to a BD appends to the manager's
  `assignments.jsonl`; the BD's app shows it as "Assigned to you"; Accept
  copies the lead into the BD's folder with a `sourceRef`. The researcher's
  app shows "With Ravi" by reading the assignment. Same for handing over a
  leaver's leads.
- **Sync** (button, on app start, and every 30 minutes while signed in):
  `git pull --rebase --autostash`, then stage **only** the paths this person
  may write, commit `sync: <username> <ISO time>`, push. On a rejected push,
  pull and retry once. On any conflict or missing GitHub sign-in: abort
  cleanly, keep local files, and show the exact sentence the person should
  say to their Claude ("Fix the Outreach Kit sync" / "Set up GitHub sign-in
  for the Outreach Kit"). Sync never stages code, so a teammate can't push
  code by accident.
- **A `Store` interface** (`src/lib/store/`) is the only code that touches
  `team/`. Pages and actions call the Store, never `fs`. A server database
  later replaces the file Store without touching the screens.
- **The owner's code updates arrive by the same pull.** `pnpm dev` hot
  reloads; if `package.json` or the lockfile changed, the app shows "Restart
  needed: ask Claude to restart the Outreach Kit", and `predev` runs
  `pnpm install` when the lockfile changed.

## What this setup can't do (state it in the README, don't hide it)

- **Logins identify people; they don't protect data.** Every laptop that
  pulls has every folder. The app shows a BD only their own leads, but the
  files are readable on disk. The owner accepted this.
- **Account changes reach a laptop at its next sync**, not instantly.
- **The real way to remove someone** is removing their GitHub access to the
  repo, then disabling the account. They keep whatever was already on their
  laptop.
- **Duplicate checks are as fresh as the last sync.**
- **Lead contact details stay in git history.** The repo must be private.

## Decisions (settled by the owner)

- **One workspace; the owner is the only super admin.**
- **Territories are shared.** Any BD may build and save a kit for any
  category and city. The save shows who else works it (names and lead
  counts only).
- **A BD sees only their own leads.**
- **Duplicates are blocked.** Adding a business that is already someone's
  lead (same Maps place key, same phone digits, or same normalised name +
  city) is refused with "Smith Roofing is already Ravi's lead." Nothing else
  about Ravi's lead is shown. Checked across every folder on the laptop.
- **Researcher leads go to an unassigned queue**; a manager (their team) or
  an admin assigns each one to a BD.
- **Export:** BD own, manager team, admin and super admin all; researcher and
  viewer none. Every export is written to the exporter's `audit.jsonl`.
- **Teammates use Mac and Windows.** Every script is Node (`tsx`), no shell
  scripts, no Mac-only tools, `path.join` everywhere.

## Accounts and sessions

- **Username and password.** Usernames: 3–30 characters, lower-case letters,
  digits, dot and underscore, unique (they are also folder names).
- **Creating an account** (super admin: any role; admin: manager, bd,
  researcher, viewer) takes full name, username, role and team. The app
  generates a temporary password, stores only its bcrypt hash
  (`bcryptjs`, cost 12: pure JavaScript, nothing to compile on Windows) in `team/users/<username>.json`, and shows the
  password **once** with Copy: "Username … · Temporary password … · Ask
  your Claude to set up and run the Outreach Kit, then sign in at
  http://localhost:3000".
- **First sign-in forces a new password** (10+ characters), stored as a hash
  in the person's own `profile.json` with `basedOnRev` = the user file's
  `rev`. The password that works is the own one when `basedOnRev` equals
  the current `rev`, otherwise the temporary one. That lets an admin reset a
  password without writing into the person's folder.
- **Reset password, suspend, disable, enable, change role, move team** bump
  `rev` in the user file. Same rule as creation: super admin over everyone,
  admin over the four roles below admin, nobody over themselves (except
  their own password). The platform always keeps the owner as super admin;
  the workspace always keeps one active admin or super admin.
- **States:** `active`; `suspended` (reason, optional end date, keeps their
  leads; lifts itself when the date passes); `disabled` (left: refused until
  their open leads have handover records). No account is ever deleted.
- **Sessions last a fixed 14 days from sign-in.** An httpOnly, `sameSite=lax`
  cookie signed with HMAC-SHA256 holds `{ username, issuedAt, rev }`. The
  secret is generated on first run into `.local/session-secret`. Every
  request re-reads the user file: session ends if older than
  `SESSION_DAYS = 14`, if `rev` changed, or if the account isn't active.
  Signing out ends it at once.
- **One error for every failed sign-in:** "That username and password don't
  match, or the account is not active." After 5 failures in 15 minutes for a
  username on this laptop, wait 15 minutes.

## Guardrails (read twice)

- **The port is untouched.** Don't edit `generateKit`, `openers`,
  `messages`, `buildPromptText`, `src/data`, `src/content`, the local
  `SEQUENCE`, `applyCategoryKit` or `src/kits/*.json`. `pnpm parity`,
  `pnpm golden:sweep`, the goldens in `golden/` and `golden/v2/`, and
  `CHANGES.md` pass with **no changes**.
- **The Kit Console keeps its four steps and its output.** Only its props
  change. `SaveKit` is replaced through the existing `actions` slot.
  `KitView` is unchanged.
- **A saved kit still stores inputs only** and is rebuilt on view.
- **Score and tier stay computed** with `src/lib/leads/score.ts` (the SQL
  generated columns go away). Stage-change events are written by the Store,
  replacing the SQL trigger. `src/lib/leads/sequence.ts`, `ratios.ts`,
  `csv.ts` and `import.ts` keep their behaviour; the CSV keeps the exact
  28-column header.
- **One permission map, no role names in components.** Code asks
  `can(session, "users.reset_password")`, never `role === "admin"`. Every
  server action and page calls `requirePerm()`. The Store refuses any write
  outside the caller's own folder (and, for admins, the three team files).
- **Writes are safe on Windows:** write to a temp file in the same folder,
  then rename; retry the rename up to 5 times on `EPERM`/`EBUSY`. JSON is
  written with sorted keys and a trailing newline so git diffs stay small.
  Add `.gitattributes` with `team/** text eol=lf`.
- **Passwords:** only bcrypt hashes are written; never logged, never in
  `audit.jsonl`, never in a URL, never in a commit message.
- **No secret is committed.** `.local/` is gitignored. `pnpm secrets:check`
  (run by `predev` and `pnpm test`) fails if a session secret, a
  plain-text password field, or a `.env` file is tracked.
- **The app never sends outreach and sends no email.** Notifications are
  in-app only.
- **Brand rules bind every new screen.** Four colours, Jost 400/500 only, no
  `<b>`, Electric Blue never for small text. `pnpm brand` passes with no new
  exemptions.
- **BD and researcher screens work at 390px.**
